# Audit of the five research notebooks

## Scope

The following notebooks were inspected:

- `3sforecaster-cif (1).ipynb`;
- `3sforecaster-m3.ipynb`;
- `3sforecaster-m4 (3).ipynb`;
- `3sforecaster-tourism (1).ipynb`;
- `3sforecaster-casagres (6).ipynb`.

Together they contain approximately 42,000 non-empty code lines. Thirty-three exact duplicate code-cell groups were identified, accounting for 109 duplicated cell instances. The principal source of notebook size was repeated declaration of metrics, model classes, baseline wrappers, optimization objectives, and analysis functions.

## Canonical source selection

- The M4 notebook was used as the principal source for the complete S3-Forecaster, S3-FastSketch, baseline, data-efficiency, and multi-prior workflows.
- The CASAGRES notebook was used as the principal source for the extended S3-FastSketch ablation logic.
- CIF, M3, and Tourism were used to verify repeated protocols and dataset-specific differences.
- Dataset ingestion was intentionally not merged into the model package because the raw schemas and file layouts differ. The notebooks should retain only loading and train/test-map construction.

## Consolidation decisions

### 1. Metrics

Several notebook cells used `MAPE` as a fraction, whereas others multiplied by 100 and labeled it as a percentage. The unified API exposes both `mape` and `mape_percent`; paper tables use `MAPE (%)`. This prevents silent factor-of-100 inconsistencies.

The unified metric module also centralizes MAE, MSE, RMSE, R², sMAPE, ECP, coverage error, interval width, interval score, MSIS, elapsed time, and trainable-parameter counts.

### 2. Test-set isolation

One FastSketch uncertainty-optimization workflow evaluated candidate interval parameters using `test_full`. The refactored implementation creates a chronological validation block from the training set and reserves the final test data for one evaluation after model selection.

### 3. Fixed-parameter secondary analyses

Ablation, data-efficiency, shock, and multi-prior analyses now reuse the selected point and UQ hyperparameters. Independent reoptimization after removing a component would confound component contribution with compensatory tuning.

### 4. Shock detection

Shock thresholds are estimated from training seasonal innovations. The test set is labeled only after the threshold has been fixed. This preserves the pre-test nature of the analysis.

### 5. Optional dependencies

TensorFlow, PyTorch, Prophet, Chronos-like models, and KAN implementations are loaded only when their corresponding baseline or prior is instantiated. Core experiments therefore require only NumPy, pandas, SciPy, scikit-learn, statsmodels, Optuna, and Matplotlib.

### 6. Parameter accounting

The reported parameter count includes fitted readout coefficients and intercepts, plus optimized scalar gate parameters where applicable. Fixed reservoir weights and deterministic sketch filters are not classified as trainable parameters.

## Recommended notebook reduction

Each dataset notebook should contain only:

1. package installation/imports;
2. dataset loading and schema-specific cleaning;
3. construction of `train_series_map` and `test_series_map`;
4. dataset-level configuration;
5. calls to the package functions;
6. result visualization or export.

Model classes and reusable functions should not be redeclared inside dataset notebooks.

## M4 replacement notebook

The original `3sforecaster-m4 (3).ipynb` has been analyzed and replaced by:

```text
notebooks/3sforecaster_m4_repository_reproduction.ipynb
```

A Kaggle CPU copy is generated at:

```text
kaggle/s3forecaster_s3fastsketch_m4_cpu.ipynb
```

Both notebooks are generated by `tools/make_m4_kaggle_notebook.py`.
The Kaggle notebook embeds a zipped copy of `s3paper/` as a fallback so it can
run even when a source dataset is not mounted by the worker.

The replacement notebook keeps the source notebook's dataset protocol:

1. downloads the official M4 Monthly train, test, and info CSV files from `Mcompetitions/M4-methods`;
2. selects row 0 / series `M1`;
3. applies the positive-only log transform used by the source notebook;
4. constructs monthly `pd.Series` objects for train and test;
5. evaluates the same result families through package APIs rather than inline class/function definitions.

The source notebook contained 48 cells and 206 inline function/class definitions. The generated replacement has 26 cells and delegates repeated logic to the `s3paper` modules listed above.

Fixed parameters recovered from the source notebook are embedded in the replacement notebook for CPU-friendly reruns. The notebook also exposes `RUN_OPTUNA`; when set to `True`, it reruns training-only hyperparameter searches through the repository experiment helpers.

The replacement exports the following CSV artifacts:

- `proposed_models_summary.csv`;
- `baseline_summary.csv`;
- `ablation_summary.csv`;
- `shock_vs_non-shock_results_final.csv`;
- `data_efficiency_analysis.csv`;
- `robustness_table.csv`.
